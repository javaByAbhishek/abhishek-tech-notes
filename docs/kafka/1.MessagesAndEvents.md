# 1. What Is an Event?

Apache Kafka helps us build event-driven microservices.

An event in Apache Kafka is an indication that something has happened.

## Examples

* When a user logs in to a website, a new event is generated to indicate that a login took place.
* When a new product is created, a microservice can publish a **Product Created Event**.
* When a new order is placed, an event is generated to indicate that the order has been placed.

## Purpose of Events

Events are used to represent changes in the state of an application or system.

In other words:

> **Event = a way of saying that something has changed in your application or system.**

---

# 2. Event Naming Convention

In event-driven microservices, there is usually a naming convention for events.

## Naming Rules

Event names should:

* Be in simple past tense.
* Start with a noun.
* Follow with the performed action.
* End with the postfix **Event**.

### Pattern

**Noun + Performed Action + Event**

## Examples

* New product created → **Product Created Event**
* Product shipped → **Product Shipped Event**
* Product deleted → **Product Deleted Event**

The event name therefore describes something that has already happened.

---

# 3. Kafka Message vs. Kafka Event

The terms **Kafka message** and **Kafka event** are often used interchangeably.

Many tutorials and books about event-driven microservices also use **event** and **message** interchangeably.

However, we can understand their relationship using an envelope analogy:

* **Kafka Message** → the message envelope
* **Event Data** → the content inside the envelope

So, the Kafka message carries the event data.

---

# 4. Event Data / Message Payload

The event data, or message payload, can have different formats.

It can be:

* A simple String
* A JSON payload
* Another data format
* Even `null`

Basically, anything that can be serialized into an array of bytes can be used as a payload.

## JSON Example

If JSON representation is used, the event payload could contain a JSON representation of a product.

For example:

1. A product is created by the Products microservice.
2. The product is represented as JSON.
3. It is published as event data.
4. Other microservices subscribed to this information receive the event.

---

# 5. Kafka Message Payload Size

The default message payload size is **1 MB**, which is enough in most cases.

However, Kafka messages are sent over the network, so message size matters.

**Larger message → potentially slower system performance**

Ideally, the event object should contain all the information about the event that the consuming microservice needs.

However, if the event becomes very large, consider optimizing it.

## Example: Images and Videos

If you need to include an image or video file, it is better to:

* Store the file separately.
* Include a link to the file in the event.

Rather than:

* Serializing the entire image/video into the Kafka message.

---

# 6. Serialization and Deserialization

Whatever information is included in the message payload must be converted before being stored in Kafka.

## Producer → Kafka → Consumer Flow

1. The producer microservice creates the message payload.
2. The payload is serialized into an array of bytes.
3. It is sent over the network.
4. It is stored in a Kafka topic as a byte array.
5. The consumer microservice receives the message.
6. The payload is deserialized into the destination data format.

### Flow

```text
Producer → Serialize → Byte Array → Kafka Topic → Consumer → Deserialize → Destination Format
```

# 7. Main Parts of a Kafka Message

Three main and frequently used parts of a Kafka message are:

* **Message Payload / Value**
* **Message Key**
* **Timestamp**

Kafka messages can also contain additional elements such as **Headers**.

---

## 7.1 Message Payload / Value

The value contains the event data.

It can contain different data types, including:

* String
* JSON
* Other formats
* `null`

The value is serialized into an array of bytes before being stored in Kafka.

---

## 7.2 Message Key

The second main part of a Kafka message is the message key.

A message key:

* Can have different data types.
* Can also have a null value.
* Is serialized into an array of bytes by the producer microservice before being stored in the Kafka topic.

Therefore, a Kafka message can be thought of as a:

> **Key–Value Pair**

Both the key and value can have different data types, including `null`.

### Example Key

A key could be:

* An alphanumeric string of characters
* A value with a custom format

Message keys will also be important when learning how Kafka events can be ordered.

---

## 7.3 Timestamp

The third important part of a Kafka message is the timestamp.

The timestamp can be:

* Set by the system, or
* Set manually

## Why Is a Timestamp Important?

A timestamp is useful when you need to know:

> **At what time in history did the event take place?**

---

## 7.4 Headers

Kafka messages can also contain headers.

Headers are a list of key-value pairs used to include additional metadata information in a Kafka message.

### Example

A header could contain an authorization header that the destination microservice needs to access user-protected resources.

However:

* Headers are optional.
* Some applications may never need to use them.

Kafka messages can contain other details as well, but **payload/value, key, timestamp, and headers** are the main elements covered here.

---

# 8. Kafka Message Structure

A Kafka message can be visualized as:

```text
Kafka Message
│
├── Key
│   └── Serialized as bytes
│
├── Value / Event Data
│   └── Serialized as bytes
│
├── Timestamp
│
└── Headers (Optional)
    └── Key-value metadata
```

The most important concept is that the producer serializes the key and value into bytes, Kafka stores them, and the consumer deserializes the data into the required format.
