# Kafka Producer Idempotence
## Why Enable Idempotence?

Kafka producers and Kafka brokers communicate with each other over a **network**. Because of this, network errors can occur even after a message has been successfully stored by the Kafka broker.

### Happy Path Scenario

The normal message flow is:

1. The **Kafka producer** sends a message to the **Kafka broker**.
2. The broker receives the message.
3. The broker stores the message in a **Kafka topic**.
4. Once the message is successfully stored, the Kafka broker sends an **acknowledgement** back to the producer.
5. The producer receives the acknowledgement successfully.

This is the **happy path scenario**.

### Problem Caused by Network Failure

A problem can occur when the broker has successfully stored the message, but the acknowledgement does not reach the producer because of a network error.

The sequence is:

1. The Kafka producer sends a message to the Kafka broker.
2. The Kafka broker receives and stores the message in the Kafka topic.
3. The Kafka broker sends an acknowledgement to the producer.
4. A **network error** occurs, so the acknowledgement does not reach the producer.
5. If **producer retries** are configured, the producer sends the **same message again**.
6. The Kafka broker receives the message again.
7. The broker stores the same message in the Kafka topic again.
8. The broker sends another acknowledgement.
9. This time, the acknowledgement successfully reaches the Kafka producer.

### Result: Duplicate Messages

The problem is that the Kafka topic now contains **two identical messages**.

Duplicate messages may not be a major problem in some applications, but they can be a very serious problem in others.

Examples:

- **Banking application:** A user's bank account could be **charged twice**.
- **Online store:** A product could be **shipped to the customer twice** instead of once.

Therefore, in some applications, duplicate messages can cause serious problems.

## Idempotent Producer

To avoid situations involving duplicate messages, the Kafka producer can be made **idempotent**.

An **idempotent producer** avoids duplicate messages in the log in the presence of **failures and retries**.

### Meaning of Idempotence

In simple terms:

- The producer can send the **same message multiple times**.
- The Kafka broker will **only store the message once**.
- The message will remain in the **correct order**.
- This helps prevent **inconsistency in the Kafka topic**, even when there are problems with the network or servers.

## Message Flow with Idempotence Enabled

Once **Idempotence** is enabled in the Kafka producer, the application works differently.

The sequence is:

1. The producer sends a message.
2. The Kafka broker stores the message in the Kafka topic.
3. Once the message is stored, the Kafka broker sends an acknowledgement back to the producer.
4. A network problem occurs, and the acknowledgement does not reach the Kafka producer.
5. The producer sends the **same message again**.
6. Because **Idempotence** is enabled, the Kafka broker recognizes that the producer is sending the same message again.
7. The broker sees that there is **already a message like this in the Kafka topic**.
8. Instead of storing the same message again, the Kafka broker simply acknowledges that it already has the message.
9. Even if the Kafka producer sends the same message multiple times, there will be **only one such message in the topic**.

### Result

With an idempotent producer:

- The same message can be sent multiple times because of retries.
- The broker does not store duplicate copies.
- The topic contains **only one copy of the message**.
- This prevents **duplicate messages** and helps prevent inconsistency.

# Enabling Idempotence

To enable Idempotence in a Kafka producer, the relevant **configuration property must be set to `true`**.


- `Application.properties`
- **spring.kafka.producer.properties.enable.idempotence=true**

## Idempotence Is Enabled by Default

In newer versions of Kafka, the **Idempotence configuration property is already set to `true` by default**.

Therefore:

- Idempotence is already **enabled by default**.
- You do not necessarily need to enable it explicitly.

However, still **recommends explicitly setting the property to `true`**.

### Why Explicitly Enable It?

It is very easy to accidentally disable Idempotence.

If the Idempotence property is not explicitly set to `true`, certain other Kafka producer configuration properties can be set to **conflicting values**.

When those properties have conflicting values, they can **disable the default Idempotence configuration**.

Therefore, explicitly setting the Idempotence property to `true` helps make sure that Idempotence remains enabled.

## Configuration Requirements

For Idempotence to work correctly, several Kafka producer configuration properties must have appropriate values.

| Configuration Property | Required Value |
|---|---|
| **Acknowledgement property** | Must be set to the value required for Idempotence |
| **Retries** | Must be **greater than zero** |
| **Maximum in-flight requests per connection** | Must be **equal to or less than 5** |

### Retries

**All retries must be greater than zero.**

Retries are important because Idempotence is specifically intended to handle situations where failures cause the producer to send a message again.

### Maximum In-Flight Requests Per Connection

The **maximum in-flight requests per connection** configuration determines how many requests or batches of messages the Kafka producer can send to the broker at the same time **without waiting for acknowledgements**.

The lecture specifies that the value must be **equal to or less than 5** for an idempotent producer.

#### Benefits

Allowing multiple requests or batches to be in flight at the same time can:

- Improve **throughput**.
- Improve the **performance of the broker**.

#### Risk

However, having multiple in-flight requests also introduces a risk of **message reordering** in case of failures and retries.

Keeping the maximum in-flight requests per connection at **5 or less** is important for an idempotent producer to:

- Maintain the **right order**.
- Avoid **message loss**.

## Conflicting Configuration Values

If the relevant Kafka producer configuration properties are set to **conflicting values**, the default Idempotence configuration will be **disabled**.

Therefore, even though Idempotence is enabled by default in newer Kafka versions, it can still be disabled accidentally through conflicting configuration settings.

### Recommended Configuration

To make sure Idempotence is enabled:

1. **Explicitly set the Idempotence configuration property to `true`.**
2. Make sure the other relevant configuration properties do not have **conflicting values**.
3. Ensure that:
    - **Retries > 0**
    - **Maximum in-flight requests per connection ≤ 5**
    - The **acknowledgement property** is set to the value required for Idempotence.

## Configuration Exception

If you explicitly enable the Idempotence property but set other configuration properties to **conflicting values**, a **config exception** will be thrown in the application.

Therefore:

- Idempotence is **enabled by default** in newer Kafka versions.
- Conflicting configuration values can **disable the default Idempotence configuration**.
- Explicitly setting Idempotence to `true` while using conflicting configuration values results in a **config exception**.
