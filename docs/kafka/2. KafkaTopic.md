# Kafka Topics

A **Kafka Topic** is a place where Kafka stores all published messages/events. Topics provide a way for producer microservices to publish events without directly sending them to individual destination microservices.

## Kafka Topic Architecture

Consider a system with:

* A **Products Microservice**
* An **SMS Notification Microservice**
* An **Email Notification Microservice**
* A **Push Notification Microservice**

Each notification microservice wants to be notified whenever a new product is created.

When a new product is created:

1. The **Products Microservice** publishes an event.
2. Instead of sending the event directly to a destination microservice, the **Kafka Producer** stores the event in a **Kafka Topic**.
3. The microservices interested in the event read it from the Kafka Topic.
4. The same event can therefore be consumed by the SMS, Email, and Push Notification Microservices.

### Topics and Durability

Kafka topics are **partitioned**, and each partition is **replicated across multiple Kafka servers** for durability.

This means:

* Data is stored across multiple Kafka servers.
* If there is an issue with one Kafka server, the data is still stored on other Kafka servers.
* Events published by the Products Microservice are first stored in the Kafka Topic.
* Microservices interested in those events read them from the topic.

## Kafka Topic Names

When working with a Kafka Topic, you refer to it by its **name**.

* Each topic that is created has a **unique name**.
* In the lecture example, the topic is named:

**`product-created-event-topic`**

The topic itself is divided into **partitions**.

---

## Kafka Topic Partitions
In the example, the Kafka Topic is divided into **three partitions**:

* Partition 0
* Partition 1
* Partition 2

Partitions are useful because consuming microservices can read data from different topic partitions **in parallel**.

This can help:

* Increase **throughput**
* **Scale** the application
* Make the system work **faster**

### Horizontal Scaling with Partitions

If a topic has more than one partition, the application can be **horizontally scaled**.

For example:

1. Create a topic with multiple partitions.
2. Run separate instances of the same microservice.
3. Each instance can read from its own partition in parallel.
4. Events can therefore be processed much faster than when only one microservice instance is running.

If one microservice instance is still busy processing one event, **other instances can pick up other events from the topic and process them in parallel**.

The lecture notes that how multiple instances of the same microservice are started and made to work together as a group will be covered in following lectures.

---

## Creating and Changing the Number of Partitions

The number of partitions is specified **when the topic is created**.

After the topic has been created:

* The **number of partitions can be increased** if needed.
* Apache Kafka **does not support reducing the number of partitions** for a topic.

Therefore:

> **You can increase the number of partitions, but you cannot decrease them.**

---

## Topic vs. Partition

The **topic itself is a logical concept** in Kafka.

A **partition**, however, is an actual small storage unit that:

* Holds event data.
* Is stored on a **hard disk on a Kafka server**.

In the lecture example, the topic contains three partitions. Each partition is represented like a table row containing cells where event data is stored.

For example:

* Partition 0 contains several event entries.
* Each cell contains event data.
* Each event entry has a number associated with it.

## Kafka Offsets

Each event stored in a partition is assigned a number called an **offset**.

An **offset** is similar to an **index in a Java array** because it starts at **0**.

For example, in Partition 0:

| Event        | Offset |
| ------------ | -----: |
| First event  |      0 |
| Second event |      1 |
| Third event  |      2 |
| Fourth event |      3 |
| Fifth event  |      4 |

When the very first event is stored in Partition 0, it receives **offset 0**.

The next event stored in the same partition receives **offset 1**.

Every time a new event is stored in that partition, its offset increases by **one**.

---

## Kafka Topics Are Append-Only

A Kafka Topic/partition is **append-only**.

This means:

* A new event is **always added at the end**.
* You cannot insert a new event somewhere in the middle of existing events.
* Once a message is persisted, the next new message receives the next offset.

For example:

```text
0 → 1 → 2 → 3 → 4 → 5 → ...
```

A new event is appended after the existing events rather than inserted between them.

### Key Rule

**New events are always added at the end of a partition.**

---

## Events Are Immutable

Event data stored in a partition is **immutable**.

Once an event has been stored:

* You **cannot change** it.
* You **cannot delete** it.
* You **cannot update** it.
* You **cannot insert another event in the middle** of the existing events.

The lecturer compares this to real life: if a certain event took place, you cannot change history or undo that event.

### Important Properties

| Property                       | Kafka Partition     |
| ------------------------------ | ------------------- |
| Add new event                  | **Yes, at the end** |
| Change existing event          | **No**              |
| Delete existing event          | **No**              |
| Update existing event          | **No**              |
| Insert between existing events | **No**              |

---

## Ordering of Events

Events are stored **in order within an individual partition**.

However:

> **Order across partitions is not maintained.**

Different partitions can therefore contain different numbers of events.

For example, one partition may contain events at offsets `0–4`, while another partition may contain only events at offsets `0–2`.

The important distinction is:

* **Within a partition:** events are stored in order.
* **Across partitions:** a global order is **not maintained**.

---

## Events Remain After Consumption

When an event is consumed from a Kafka Topic, **the event is not deleted**.

The event remains in the topic after it has been consumed.

Therefore:

* Consuming an event does **not** remove it from the partition.
* The event can remain stored for as long as the configured retention period allows.
* Kafka does not keep the event forever by default.

---

## Kafka Topic Retention

By default, a Kafka Topic is configured to retain events for **seven days**.

The retention period can be changed through **configuration properties**.

Therefore, the default behavior is:

* **Default retention time: 7 days**
* The value can be changed if needed.
* Kafka topics can be configured to keep data for longer or for the required period.

### Important Distinction

**Consumption does not delete an event.**

Instead, Kafka retains the event according to the topic's **retention configuration**.
