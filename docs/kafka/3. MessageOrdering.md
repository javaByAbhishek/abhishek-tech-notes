# Apache Kafka — Messages and Events

## Message Ordering in a Kafka Topic

A key concept when working with Apache Kafka is understanding **the order in which events are stored and processed in a Kafka topic**.

Consider a Kafka topic called **`profile-updated-event-topic`**.

Every time a user updates their profile, a new event is published to this topic. For example, suppose a user changes the spelling of their first name and clicks the update button.

A new event is published and persisted into a Kafka partition. The user then changes the spelling of their first name again and updates the profile, resulting in another event. A third update produces another event, which may be stored in yet another partition.

The important issue is that, depending on how the messages are partitioned, the consumer may not process these events in the same order in which they were originally published.

## Kafka Messages as Key-Value Pairs

A Kafka message is a **key-value pair**:

* **Message key** — can be a string value.
* **Message value** — contains the event details, which can be represented as a **JSON payload**.

The message key is particularly important when the **order of related events must be preserved**.

### When No Message Key Is Provided

If a **message key is not provided**, an event can be stored in any of the available partitions.

For example, if a topic has three partitions:

* Partition 0
* Partition 1
* Partition 2

Kafka makes the partition-selection decision.

When no message key is provided, **Kafka will try to load balance events** by storing a new event in one of the available partitions.

Therefore, consecutive events related to the same user can end up in different partitions.

## Consumers Read Partitions in Parallel

Another important detail is that a **consumer microservice consumes events from topic partitions in parallel**.

Because the consumer reads events from different partitions in parallel, there is **no guarantee about the order in which the consumer microservice will receive those events**.

For example, suppose three events are:

* **A**
* **B**
* **C**

The events may have been published in the intended order:

**A → B → C**

However, because the events can be stored in different partitions and those partitions are read in parallel, the consumer could receive them in different orders, such as:

* **A → C → B**
* **B → A → C**
* **C → B → A**

The lecture illustrates several possible processing orders for the events.

### Why This Can Be a Problem

This becomes a problem when **the order in which events should be processed is important**.

For example, if the correct processing order is:

**A → B → C**

but the consumer processes the events in another order, the user's first name could be updated in the database with an **incorrect value**.

Therefore, when the order of events is important, a mechanism is required to ensure that related events are processed in their original order.

# Message Key and Event Ordering

In situations where **event ordering is important, we should always provide a message key**.

When a message key is provided, Kafka uses that key to determine **which partition the event should be written to**.

The important rule is:

> **Events with the same message key are stored in the same topic partition.**

This allows Kafka to preserve the ordering of related events.

## How Kafka Uses the Message Key

Kafka takes the message key, **hashes it**, and then uses the resulting hash value to determine which partition should be used to store the event.

For example:

1. A message is published with a particular message key.
2. Kafka hashes the message key.
3. The hash value is used to determine the target partition.
4. The event is stored in that partition.
5. Another event with **exactly the same message key** is published.
6. Kafka uses the same message key to determine the same partition.
7. The second event is therefore stored in the **same partition** as the first event.

This means that Kafka always stores messages with the **same message key in the same partition**.

### Example Using a User ID

Suppose the **user ID** is used as the message key.

If the first profile-update event for a user is stored in **Partition 0**, then another profile-update event using exactly the same user ID as its message key will also be stored in **Partition 0**.

For example:

**Event A → Partition 0**

**Event B → Partition 0**

**Event C → Partition 0**

Because the events have the same message key, they are grouped into the same partition.

## Why This Provides Ordering

Kafka's use of the message key helps achieve **ordering of related events**.

If events with the same message key are persisted to the same partition, then those events remain in the same partition in the order in which they were persisted.

When the consumer microservice reads events from the topic:

* It can still read events from **other partitions in parallel**.
* However, events with the **same message key** are located in the same partition.
* Their processing order will therefore be the same as the order in which those events were persisted.

This is how Kafka can help achieve **ordering of events**.

# Choosing a Message Key

A Kafka message can contain several elements, and one of these elements is the **message key**.

The message key can use **different data types**.

If a simple **String** is used, possible message-key values include:

* **Product ID**
* **User ID**

The choice of message key depends on the type of events being produced.

## User-Related Events

If the producer microservice publishes user-related events, such as:

* Updating user details
* Updating a user's profile

then **User ID** can be selected as the message key.

The message key does not necessarily have to be the actual user ID stored in the database. A different value can be generated.

However, the lecture notes that it is often easier to use an **existing value**, such as the user ID.

## UUID as a Message Key

If the message key uses the **String** data type, a **UUID** can be used to generate a unique alphanumeric string of characters.

The lecture also shows that a producer can create a **custom format for message keys**.

Therefore, the exact message-key format can be chosen according to the application's requirements.

# Grouping Related Events

The most important rule when using message keys for ordering is:

> **To store related events in the same topic partition, each of those events should have the same message key.**

For example, suppose events are related to products.

All events related to **one particular product** can be grouped together under one ID.

Events related to **another product** can be grouped together under another message ID.

This allows related events to be stored in the same partition.

### Product Example

Suppose:

* Events related to Product 1 use one message key.
* Events related to Product 2 use another message key.

Kafka will use those message keys to determine the partitions in which the events are stored.

The events associated with the same product therefore use the same message key and are stored in the same partition.

This is needed so that the **consumer microservice can process events related to the same product in the same order in which they were published**.

# Key Revision Points

* A Kafka message is a **key-value pair** consisting of a message key and message value.
* The **message value** can contain event details in the form of a **JSON payload**.
* When a **message key is not provided**, Kafka can store events in different available partitions and tries to **load balance** them.
* A consumer microservice can read events from topic partitions **in parallel**.
* Because of parallel consumption, events stored in different partitions **may not be received in their original overall order**.
* If event ordering is important, **a message key should be provided**.
* Kafka uses the message key to determine the partition in which an event is stored.
* Kafka **hashes the message key** and uses the hash value to determine the partition.
* Events with the **same message key are stored in the same topic partition**.
* Keeping related events in the same partition allows their **processing order to be preserved**.
* Suitable String message keys can include a **User ID**, **Product ID**, a **UUID**, or a **custom message-key format**.
* For related events to be stored in the same partition, **each related event must use the same message key**.
* This allows the consumer microservice to process events related to the same user or product **in the same order in which they were published/persisted**.

## Core Rule to Remember

**If the order of related events matters, use the same message key for all of those related events so that Kafka stores them in the same partition.**

This is how **message keys can be used to achieve ordering of events in microservices**.
