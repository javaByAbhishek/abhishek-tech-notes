# Understanding Consumers, Consumer Groups, and Partitions

## 1. Baseline Architecture Scenario (Single Consumer)
* **The Setup:** Assume we have a Kafka topic named `product created events`.
* **Partitions:** This topic is created with **three partitions**. All messages in this topic are stored across these three separate partitions.
* **The Consumer:** To consume messages from this topic, we start one microservice called `email notification microservice`, which acts as the Kafka consumer.
* **Behavior with One Consumer:** When there is only one consumer microservice, this single consumer will read messages from **all three partitions** in the topic.

## 2. Scaling Up to Two Consumers & Rebalancing
* **The Scenario:** Assume there is a large load on the application, and one instance of the `email notification microservice` is not enough. We choose to scale up the application by starting **one more instance** of the service.
* **Kafka's Reaction:** Kafka will notice that there are now two consumer applications running and will reassign the partitions among them.
* **New Distribution:** Instead of one consumer reading from all three partitions, **one instance reads messages from one partition**, and the **other instance reads data from two partitions**.
* **Rebalancing Definition:** This process of automatic partition reassignment is called **rebalancing**.
* **Timing & Impact:** It happens very quickly. However, while partitions are being reassigned, consumers stop consuming messages from the topic for a moment.
* **Triggers:** Rebalancing takes place:
* Every time a new consumer joins a consumer group.
* Every time an existing consumer leaves a consumer group.

## 3. Scaling Up to Three Consumers
* **The Scenario:** We decide to scale up the application even more and start **one more** `email notification microservice` (making it three instances total).
* **Behavior:** Partition rebalancing automatically takes place again, and the partitions are reassigned.
* **Kafka's Goal:** During partition reassignment, Kafka tries to make sure that **each partition is consumed by exactly one consumer** in a group.
* **Parallel Processing:** Once this rebalancing is complete, all three consumers in the group continue to consume messages from their newly assigned partitions in parallel.

## 4. The Scaling Limit: Scaling Beyond the Number of Partitions
* **The Scenario:** Assume we want to scale up the application even further and start **one more instance**(a fourth instance) of the `email notification microservice`.
* **The Result:** This extra instance will **sit idle** in Kafka.
* **Core Rule of Consumer Groups:** Two consumers from the same consumer group **cannot** read messages from the exact same partition.
* **Crucial Takeaway:** You cannot start more active consumers than the total number of partitions you have in the topic.
* If your topic has only **one partition**, you can start only **one consumer microservice**.
* If your topic has **three partitions**, you can scale your application by starting **three instances only**.
* If you start more instances than the number of partitions in your Kafka topic, those extra instances will sit completely idle.

## 5. Heartbeats and Failure Detection
* **Group Coordinator:** When a new Kafka consumer application starts and joins a consumer group, it begins sending signals to one of the brokers selected as the **group coordinator**.
* **Heartbeats:** These signals are called **heartbeats**.
* **Time Intervals:** Heartbeats are sent at regular time intervals. This interval can be configured, but the **default value is three seconds**.
* **Purpose:** While your Kafka consumer microservices are running, each sends heartbeat signals to the Kafka Broker to let it know: *"I'm running and I can consume new messages."*
* **Consumer Failure Handling:**
* If one of the Kafka consumers stops working, it also stops sending heartbeat signals to the Kafka Broker.
* When the Kafka Broker notices that there are no heartbeats coming from a specific consumer, it removes that consumer from the consumer group and **initiates rebalancing**.
* The broker checks how many consumers are actively running and how many partitions exist in the Kafka topic.
* It reassigns the partitions to ensure each partition is read by one consumer (re-enforcing that two consumers cannot read from the same partition).
* When this rebalancing completes, all remaining active consumers in the group resume consuming messages from their newly assigned partitions in parallel.
