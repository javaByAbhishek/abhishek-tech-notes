# Introduction to Kafka Consumer Groups

## 1. Baseline Architecture Scenario (The Diagram)
* **The Producer:** A **products microservice** acts as the Kafka producer.
* **The Broker / Storage:** In the middle of the diagram, there is a **Kafka topic**.
* **The Consumers:** On the right side of the diagram, there are **three different microservices** acting as Kafka consumers:
1. `SMS notification microservice`
2. `Push notification microservice`
3. `Email notification microservice`
   ![ConsumerGroup](https://github.com/javaByAbhishek/abhishek-tech-notes/blob/main/src/main/resources/assets/ConsumerGroup.png?raw=true)
### The Message Flow in this Baseline Scenario:
* The products microservice publishes a **product created event**.
* This event gets stored inside the Kafka topic.
* As soon as a new event is in the Kafka topic, the microservices that are listening for events from this topic will consume it.
* Because there are three different microservices in this example, **all three microservices will receive the new product created event message**.
* This serves as an example where you have multiple Kafka consumers reading from the exact same topic.
* This example is simple because all the microservices are different, and each of them genuinely needs to receive its own individual copy of the product created event.

## 2. The Challenge of Scaling Up Microservices
* **The Question:** What happens if we need to scale up and start more instances of a specific microservice, such as the email microservice?
* **The Setup:** Assume that we start **three more email notification microservices**, resulting in a total of **four running instances** of the email notification microservice.
* **The Multi-Service Behavior:** When a new message is published to the topic:
* The SMS notification microservice will receive its own copy.
* The push notification microservice will receive its own copy.
* **The Problem with the Scaled Instances:**
* Do we want all four running email notification microservices to consume exactly the same message? **The answer is no.**
* If they do, the exact same message will be processed by the email notification microservice **four times**.
* Even though four instances of the email notification microservice are running, we want **only one of them** to receive a new message.
* It does not matter which specific instance processes the message, as long as the message is processed **one time only**.

## 3. The Solution: Kafka Consumer Groups
* To help scale up consumer microservices, Kafka allows you to run multiple consumers together in a group.
* This mechanism is called a **consumer group**.

### Why Consumer Groups are Helpful:
* They are highly beneficial when you have a large volume of messages in a topic and you need to process them faster.
* You can start up multiple instances of the email notification microservice, group them into **one consumer group**, and have each group member pick one message from the topic.
* **Faster Processing:** Messages stored in the topic will be processed much faster because you now have multiple copies of this microservice working instead of just one microservice.
* **Exactly-Once Processing Per Group:** Even though multiple instances of the same microservice are working simultaneously, when a new message gets into the topic, it will be processed **one time only by one of the instances** inside that consumer group.
