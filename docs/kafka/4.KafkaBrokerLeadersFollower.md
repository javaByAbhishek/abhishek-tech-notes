# Apache Kafka Broker

A **Kafka Broker** can be thought of as a **Kafka Server**—a server that runs Kafka processes. A broker is a software program that runs on a computer or another machine that is intended to work as a Kafka Server.

A Kafka Broker can run on:

* A **physical computer**
* A **virtual machine**
* A computer/server in a **cloud environment**, such as Amazon Cloud or Google Cloud

Multiple brokers can be started together in a **Kafka cluster** to provide **high availability** and **fault tolerance**.

---

## Kafka Broker and Kafka Cluster

### What Is a Kafka Broker?

A **Kafka Broker** is a software application that:

* Accepts messages from **producers**
* Stores messages reliably in **topic partitions**
* Replicates data across other brokers in the cluster
* Enables **consumer microservices** to read events from topic partitions
* Handles requests from microservices
* Can be customized through a **configuration file**

The broker is responsible for the work involved in storing and serving Kafka events.

### Why Use Multiple Brokers?

To make the Kafka system **always available and fault tolerant**, multiple brokers can be started in a cluster.

For example:

* If one Kafka broker goes down, other brokers can continue running.
* The remaining brokers can continue servicing requests from microservices.
* Events can remain available because they are replicated across brokers.

Behind the scenes, the brokers work together to ensure that events are **stored reliably**.

---

## Leaders and Followers in a Kafka Cluster

In a Kafka cluster:

* One broker can act as a **leader**.
* Other brokers act as **followers**.
* Each broker hosts Kafka topics.
* Each Kafka topic stores events in **partitions**.

The responsibilities are divided as follows:

| Role         | Responsibility                                                  |
| ------------ | --------------------------------------------------------------- |
| **Leader**   | Handles all read and write requests for the partitions it leads |
| **Follower** | Passively replicates the leader's data                          |

The leader handles the operations, while followers maintain copies of the data.

### Fault Tolerance

If the leader goes down:

1. One of the follower brokers can become the **new leader**.
2. The new leader continues servicing requests.
3. Kafka can therefore maintain **high availability and fault tolerance**.

The leader and follower roles are **not permanently fixed to a particular broker**. They can change dynamically depending on broker availability.

# Kafka Leader

A **leader** is responsible for handling **all read and write requests for partitions in a topic**.

It is called a leader because it manages all operations for the topic partitions assigned to it.

### Analogy: Store Manager

The lecturer compares a Kafka leader to a **manager in a store** who is responsible for a specific section:

* All customer requests for that section go through the store manager.
* Similarly, all requests for a Kafka topic partition go through its leader.

### Writing a Message to a Partition

If a Kafka client wants to write a message into a topic partition:

1. The request goes to the **leader** of that partition.
2. The message is successfully persisted in the topic partition.
3. The message is then replicated to the other Kafka brokers acting as **followers**.

### Leader as the Source of Truth

The leader is the **single source of truth for all writes and reads in a topic partition**.

Followers replicate data from the leader in the **exact order in which it was written**.

This controlled and consistent replication process helps maintain **data consistency across the cluster**.

If followers were allowed to accept writes independently:

* Different followers could potentially have different versions of the data.
* This could lead to **inconsistencies and conflicts**.

---

# Kafka Follower

A **follower** in Kafka is a **replica of a partition**.

A follower:

* Copies all data from the leader.
* Follows the leader by replicating whatever data the leader has.
* Provides **redundancy** and **fault tolerance**.

### Why Followers Are Important

If the leader fails, one of the followers can **take over as the new leader**.

For example, if there is only **one broker** in the cluster and that broker goes down:

* The entire system goes down.
* There are **no replicas** of the data.

Having multiple brokers allows Kafka to have more followers, helping ensure **high availability of data**.

If one broker, including the leader, goes down, the data can still be available through the other brokers.

---

## Followers and Horizontal Scaling

Followers also allow a Kafka cluster to **scale horizontally**.

As more brokers are added:

* The number of followers can increase.
* **Data redundancy** can increase.
* The cluster's capacity to handle **more data and more clients** can increase.

Therefore, multiple brokers provide both:

* **Fault tolerance and redundancy**
* Greater capacity for handling data and clients

---

# Leader Distribution Across Brokers

It is **not always the same Kafka broker that acts as the leader**.

If the same broker were always the leader:

* All read and write operations would always go through the same server.
* This could create a **bottleneck**.

To avoid this, **every Kafka broker can be a leader and a follower at the same time**.

This distributes leadership responsibilities across the Kafka cluster.

---

# Leaders Are Assigned Per Partition

A very important detail in Apache Kafka is that **each partition has its own leader**.

The leader for a partition is assigned when the **topic is created**.

### Topic Creation and Partitions

When creating a topic in Kafka, the number of **partitions** for that topic is specified.

Kafka then uses its internal processes to assign a leader for each partition.

Therefore:

> **Each partition has its own leader and followers.**

---

## Example of Partition Leadership

Consider a Kafka cluster containing **three Kafka brokers**.

The brokers are identified using their **node IDs**.

There are also **two Kafka topics** stored across these brokers.

For example, for **Topic 1**:

* **Partition 0** can be assigned to **Kafka Broker 1** as its leader.
* **Partition 1** can be assigned to a different broker as its leader.
* **Partition 2** can be assigned to another broker as its leader.

Similarly, for **Topic 2**:

* Each partition can have a **different broker assigned as its leader**.

This distribution means that there is **no single Kafka server that always acts as the leader**.

### Avoiding a Bottleneck

Because leadership is distributed across partitions:

* Read and write operations do not always have to go through the same broker.
* The workload can be distributed across different brokers.
* A single Kafka server does not become a permanent bottleneck.

---

# What Happens When a Broker Goes Down?

If a Kafka server goes down, Kafka can **reassign leaders and followers**.

The purpose is to ensure that every partition has a **healthy Kafka broker to work with as a new leader**.

The general process is:

1. A broker containing a leader becomes unavailable.
2. One of the follower brokers can take over.
3. The follower becomes the **new leader** for the partition.
4. The new leader continues servicing requests.
5. Kafka can reassign roles to maintain availability and fault tolerance.

# Key Revision Points

* **Kafka Broker** is a software application that runs Kafka processes.
* A broker can run on a **physical computer, virtual machine, or cloud computer**.
* Multiple brokers can form a **Kafka cluster**.
* Multiple brokers provide **high availability and fault tolerance**.
* A **leader** handles all read and write requests for its assigned partitions.
* A **follower** is a replica of a partition and copies data from the leader.
* Followers replicate the leader's data in the **exact order it was written**.
* The leader acts as the **single source of truth for reads and writes** in its topic partition.
* Followers provide **redundancy and fault tolerance**.
* If a leader fails, a **follower can become the new leader**.
* **Every Kafka broker can be a leader and a follower at the same time**.
* Leadership is assigned **per partition**, not permanently to one broker.
* Partition leaders are assigned when the **topic is created**.
* Distributing partition leadership across brokers helps prevent a **bottleneck**.
* Adding brokers can increase **data redundancy** and the capacity to handle **more data and more clients**.
* If a Kafka broker goes down, Kafka can **reassign leaders and followers** so that partitions continue working with a healthy broker.
