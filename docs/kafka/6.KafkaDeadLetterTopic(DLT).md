# Kafka Dead Letter Topic (DLT) and Deserialization Error Handling

![DLT](https://github.com/javaByAbhishek/abhishek-tech-notes/blob/main/src/main/resources/assets/Dlt.png?raw=true)
## 1. Normal Message Processing Flow

Everything works correctly as long as the messages produced by the Products Microservice are compatible with the `ProductCreatedEvent` Java class expected by the Email Notification Microservice.

The normal processing sequence is:

1. The Products Microservice creates a Product Created Event.
2. The JSON Serializer serializes the event into JSON format.
3. The producer publishes the message to the `Products` Kafka topic.
4. The Email Notification Microservice consumes the message.
5. The JSON Deserializer converts the JSON message into a Java object using the `ProductCreatedEvent` class.
6. The consumer processes the successfully deserialized message.

Key requirement: The format of the message produced by the producer must be compatible with the format and Java class expected by the consumer.

## 2. The Problem: Deserialization Failure

### 2.1 Introduction of an Incompatible Message

A new microservice, called the Admin Microservice, is introduced by another team.

Unlike the Products Microservice, the Admin Microservice:

- Uses a String Serializer.
- Publishes a message that is not compatible with the format expected by the Email Notification Microservice.

The Email Notification Microservice expects JSON messages that can be converted into a `ProductCreatedEvent` Java object. However, the message published by the Admin Microservice does not match the expected format.

### 2.2 What Happens When Deserialization Fails?

When the Email Notification Microservice consumes the incompatible message, the JSON Deserializer fails to convert it into a `ProductCreatedEvent` Java object.

As a result:

- The message cannot be deserialized.
- The consumer throws an exception.
- If the exception is not handled, the same problem occurs repeatedly.
- The consumer can become stuck in an endless loop, consuming the same faulty message again and again.

### 2.3 Deserialization Failure Scenario

The sequence of events is as follows:

1. The Admin Microservice publishes an incompatible message using a String Serializer.
2. The message is published to the Kafka topic.
3. The Email Notification Microservice consumes the message.
4. The JSON Deserializer attempts to convert the message into a `ProductCreatedEvent` Java object.
5. Deserialization fails, and an exception is thrown.
6. If the exception is not handled, the consumer repeatedly encounters the same message.
7. The consumer becomes stuck processing the faulty message instead of progressing to the next message.

Important: An unhandled deserialization exception can prevent the consumer from progressing because it repeatedly encounters the same message that it cannot process.

## 3\. Previous Solution: Recovering from Deserialization Errors

In the previous section of the course, the Kafka consumer was configured to recover from deserialization errors.

### 3.1 How the Previous Solution Works

The consumer was configured so that when a message failed to deserialize, it could:

- Skip the faulty message.
- Continue processing the next message from the Kafka topic.

This prevented the consumer from remaining stuck in an endless loop on the same incompatible message.

### 3.2 Limitation of the Previous Solution

Although this approach worked, the lecturer explains that it is only part of the solution.

The problem is that the faulty message is ignored and left sitting in the topic unprocessed.

Consequently:

- The consumer can continue processing subsequent messages.
- The faulty message is not successfully processed.
- The message is effectively ignored rather than handled in a way that allows further investigation.

Key limitation: Simply skipping a message prevents it from blocking the consumer, but it does not provide a proper way to investigate or handle that failed message later.

Ignoring messages that cannot be deserialized is therefore not the best solution.

## 4\. Dead Letter Topic (DLT)

### 4.1 Definition

A Dead Letter Topic (DLT) is a place where messages that failed to be processed due to an error are sent.

Instead of silently ignoring faulty messages, the Kafka consumer sends them to a dedicated dead letter topic so that they can be inspected and handled later.

### 4.2 Purpose of a Dead Letter Topic

The main purpose of a DLT is to preserve messages that fail during processing rather than simply ignoring them.

Using a DLT allows the team to:

- Inspect failed messages stored in the dead letter topic.
- Identify the root cause of the processing or deserialization problem.
- Take corrective actions to address the problem.
- Decide what should be done with the failed messages later.
- Potentially create a separate consumer microservice that consumes messages from the dead letter topic and processes them differently.

### 4.3 How a Dead Letter Topic Improves Error Handling

The previous approach skips the faulty message and leaves it unprocessed. The DLT approach instead sends the failed message to a separate topic.

The processing sequence becomes:

1. The Kafka consumer consumes a message from the original topic.
2. The consumer attempts to deserialize the message.
3. If deserialization succeeds, normal processing continues.
4. If deserialization fails, the message is sent to the Dead Letter Topic.
5. The consumer can continue processing subsequent messages.
6. The failed message remains available for later inspection and corrective action.

The lecturer's focus in the upcoming lessons is to configure the Kafka consumer to send messages that fail deserialization to a DLT.

## 5\. Default Naming Convention for a Dead Letter Topic

By default, the name of a dead letter topic is based on the name of the current topic.

The naming convention is:

`<original-topic-name>.DLT`

The suffix `.DLT` is added to the original topic name.

For example, if the original topic is named `Products`, the corresponding default dead letter topic name would be `Products.DLT`.

| Property | Description |
| --- | --- |
| Original topic | The Kafka topic from which the message was consumed |
| Dead Letter Topic | The topic to which messages that fail processing are sent |
| Default naming convention | Original topic name followed by `.DLT` |
| Purpose | Preserve failed messages for later inspection and handling |

## 6\. Key Takeaways

- Deserialization errors occur when a Kafka consumer cannot convert a consumed message into the expected Java object.
- A producer may publish an incompatible message if it uses a different serialization format, as demonstrated by the Admin Microservice using a String Serializer.
- An unhandled deserialization exception can cause a consumer to repeatedly encounter the same faulty message.
- Configuring the consumer to skip faulty messages allows it to continue processing, but the failed messages remain unprocessed and are effectively ignored.
- A Dead Letter Topic (DLT) provides a place to send messages that fail to be processed due to an error.
- Messages in a DLT can be inspected to identify root causes, take corrective actions, and determine how to handle them later.
- A separate consumer microservice can potentially be created to consume and process DLT messages differently.
- By default, a dead letter topic uses the original topic name with the suffix `.DLT`.
